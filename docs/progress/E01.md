## O que ficou de pé

Um workspace pnpm com duas aplicações e cinco pacotes, que instala pelo lockfile,
compila, passa lint, tipos e testes, corre uma migração numa base descartável e
**responde a verdade sobre a própria saúde** — incluindo quando a infra-estrutura
está partida.

```
apps/web         Next 16.3.4 (App Router, runtime Node) — /api/health, /api/ready, proxy request_id
apps/worker      processo de fundo — arranca, valida configuração, reporta aptidão
packages/config  validação de ambiente (zod) e registo com redacção
packages/db      Prisma 7.10.0 — schema, migração e sonda de base
packages/domain  portas do domínio (porta de média)
packages/storage condutor de disco local da porta de média
packages/ui      fichas de design partilhadas
```

## Aceites, e como cada um foi provado

### 1. Instalação pelo lockfile e build completam; lint e tipos correm separados

| Comando | Resultado observado |
| --- | --- |
| `pnpm install --frozen-lockfile` | ok — `postinstall` gera o cliente Prisma |
| `pnpm lint` | ok — **23 ficheiros** inspeccionados |
| `pnpm typecheck` | ok — 7 projectos, `tsc` por pacote |
| `pnpm test` | ok — **16 testes, 16 passaram, 0 falharam** |
| `pnpm build` | ok — `✓ Compiled`, 4 rotas |

São comandos distintos, não um agregado. `pnpm verificar` existe por
conveniência e corre os quatro em sequência; saída 0.

**O lint foi provado a valer, não por ausência de saída.** Plantei um ficheiro
com uma variável não usada e um `any`: ESLint apanhou os dois e falhou. Removido,
voltou a verde. Sem esse teste, "lint sem saída" tanto podia ser código limpo
como configuração que não olha para lado nenhum.

### 2. Migração controlada em base descartável; runtime sem privilégio de schema

A migração `20260903095445_e01_base` foi **revista à mão antes de aplicada**
(`--create-only`, SQL lido, carimbo de `schema_version` acrescentado, depois
aplicada). Corre em `bossaos_dev`, criada e destruída por `scripts/dev-db.sh`.
`migrate:deploy` é idempotente e `migrate:status` reporta sem desvio.

`./scripts/provar-separacao-de-credenciais.sh` — **0 falhas**:

```
1. Controlo negativo — a credencial do runtime está viva e trabalha?
   ok   lê app_meta
   ok   escreve em app_meta
2. O que o runtime NÃO pode fazer:
   ok   recusado: CREATE TABLE / ALTER TABLE / DROP TABLE / CREATE INDEX / TRUNCATE
3. A credencial de migração consegue o que o runtime não consegue?
   ok   migração cria e larga tabelas
```

**O detector foi ele próprio testado.** Concedi `CREATE ON SCHEMA public` ao papel
do runtime de propósito: o script passou a vermelho e devolveu saída 1. Revertido,
voltou a 0. Sem isto, os cinco "recusado" podiam vir de uma credencial partida —
o passo 1 existe exactamente para excluir essa leitura.

Nota lateral que vale registar: com o `CREATE` concedido, só o `CREATE TABLE`
passou; `ALTER`, `DROP` e `TRUNCATE` continuaram recusados por exigirem posse da
tabela. A defesa é em duas camadas, não numa.

### 3. Configuração em falta falha com mensagem útil, sem revelar credenciais

`loadEnv()` atira `EnvError` nomeando as variáveis em falta e **nunca imprimindo
valores**. Coberto por teste (`packages/config`, 11 testes) e provado no processo
real: o worker sem `DATABASE_URL` sai com **78 (EX_CONFIG)**, diz qual variável
falta, e a mensagem não contém nada com forma de credencial.

### CT-03 — indisponibilidade real, sem fingir base saudável

`./scripts/provar-prontidao.sh` levanta a **aplicação construída** e interroga-a
por HTTP em quatro estados de infra-estrutura. **0 falhas**:

| Estado da infra | `/api/health` | `/api/ready` |
| --- | --- | --- |
| base migrada | 200 `vivo` | 200 `pronto` |
| base viva, schema por migrar | 200 `vivo` | **503 `schema_por_migrar`** |
| base em baixo | 200 `vivo` | **503 `base_indisponivel`** |
| sem configuração | processo não arranca (saída 78) | — |

`/health` responde 200 nos três primeiros de propósito: vivacidade e prontidão
são perguntas diferentes, e um `/health` que consultasse a base faria o
orquestrador reiniciar a aplicação quando quem caiu foi o Postgres.

O `request_id` volta ao cliente no cabeçalho, e um `x-request-id` forjado com
JSON lá dentro é **recusado** — sem essa validação, quem faz o pedido escolhe o
que fica escrito no nosso log.

## Achados que mudaram decisões

1. **Prisma 7 tirou a URL do schema.** `datasource.url` deixou de ser suportado:
   as migrações lêem `prisma.config.ts`, o runtime recebe a sua por adaptador
   (`@prisma/adapter-pg`). Isto **melhorou** o aceite 2 — a separação entre a
   credencial que altera schema e a que só a usa deixou de depender de disciplina
   e passou a viver em dois sítios incomunicáveis do código.
2. **`prisma@7` recusa Node 23.** A máquina tinha 23.11.0. Instalei fnm e fixei
   **22.23.2** exacto no `.nvmrc`.
3. **O cliente Prisma gerado fica órfão quando as dependências mudam.** O
   `generate` aterra numa árvore com hash de *peers*; acrescentar `@types/react`
   mudou o hash e o typecheck passou a falhar contra um cliente que ninguém
   gerou. Amarrado ao `postinstall` — é o que torna `pnpm install` reproduzível.
4. **Next 16 depreciou `middleware`.** Migrado para a convenção `proxy` no
   próprio dia, em vez de nascer numa convenção a caminho de sair.
5. **`constructor(public readonly x)` não sobrevive ao Node.** Propriedade de
   parâmetro não se resolve apagando tipos, e o `--experimental-strip-types` só
   apaga: o pacote `config` **nem importava**. Só apareceu porque corri os testes
   — tinha-os escrito e não executado.
6. **`@eslint/js` não segue a versão do `eslint`.** Pus `9.40.0` de cabeça e o
   registo corrigiu-me: não existe. Lido no registo: eslint `10.9.1`,
   `@eslint/js` `10.0.1`.

7. **`NODE_ENV=development` no ambiente faz `next build` falhar.** Erro:
   `TypeError: Cannot read properties of null (reading 'useContext')` a
   pré-renderizar `/_global-error` — uma mensagem que não aponta para nada. Como
   o `.env` trazia `NODE_ENV=development`, bastava um programador carregar o
   próprio `.env` antes de construir para o build partir. Isolado por medição:

   | ambiente | `pnpm build` |
   | --- | --- |
   | sem `NODE_ENV` | 0 |
   | `NODE_ENV=production` | 0 |
   | `NODE_ENV=development` | **1** |

   Corrigido em dois sítios: o script de build fixa `NODE_ENV=production`
   (imune ao que a shell disser — verificado: com `development` exportado passa
   a sair 0), e `NODE_ENV` saiu do `.env` com a razão escrita no lugar dele.

   **Cheguei aqui depois de duas explicações erradas.** Escrevi primeiro que era
   cache podre do `.next`, depois que eram servidores `next start` órfãos a
   escrever no directório — e cheguei a comentar o código com essa segunda
   versão. Nenhuma das duas se aguentou: quatro builds limpos seguidos passavam,
   e não havia órfão nenhum na porta. Só o teste que variava **uma** coisa de
   cada vez deu a resposta. Os comentários que afirmavam a causa errada foram
   corrigidos, não apagados em silêncio.
