# Revisão do E03 — estrutura multi-tenant e isolamento de dados

**Implementou:** Lúmen JR · **Revi:** Lúmen (sénior) · **Data:** 2026-09-03
**Régua:** `docs/architecture/prova-de-isolamento.md`, escrita no E00, antes desta etapa.

## Veredicto: **não validado**. O isolamento está certo; o instrumento que o prova não está.

Uma etapa cuja entrega é *isolamento **verificável*** não fecha com o verificador a
conseguir dizer verde sem ter medido nada. É o mesmo critério que aplicei ao E02 — lá era
um aviso que avisava e não impedia; aqui é uma prova que passa sem correr.

## O isolamento está provado. Refiz tudo.

| Verificação | Como | Resultado |
| --- | --- | --- |
| `./scripts/provar-isolamento.sh` | Node 22.23.2, o do `.nvmrc` | **0 falhas** — 7 grupos, 28 asserções |
| Controlo negativo dele | RLS desligado nas seis tabelas | caso 2 e caso 3 ficam vermelhos, e religa |
| **`WITH CHECK` em todas as políticas** | consulta minha ao `pg_policies` | as seis `ALL` têm `USING` **e** `WITH CHECK` |
| **As duas políticas `SELECT` extra** | li o `qual` de cada uma | `identidade_le_as_suas`, presas a `app_utilizador_actual()` |
| `pnpm verificar` | sem pipes | **0** |
| `coverage.csv` | `git diff` | **não mexeu**, como a etapa exige |
| **CI numa máquina limpa** | GitHub Actions, base do zero | **verde**, 3m10, com o passo do isolamento |

A verificação do `WITH CHECK` foi minha e é a que mais me interessava: uma política só com
`USING` lê bem e deixa **escrever** para outro inquilino. Não é o caso. E fui ver as duas
políticas `SELECT` a mais porque no PostgreSQL políticas permissivas somam-se por **OR** —
uma política de leitura extra pode alargar o acesso sem aparecer em teste nenhum. São
legítimas: deixam cada utilizador ver as organizações de que é membro, que é o que tem de
funcionar antes de haver contexto.

## O defeito

`scripts/provar-isolamento.sh:64`.

```zsh
if correr /tmp/bossaos-iso-ligado.txt; then
  verde "$(grep -c '^ok ' …) grupos verdes, $(grep -oE '^# pass [0-9]+' …) asserções"
```

O passo 1 — *"com as políticas LIGADAS, os quatro casos têm de passar"* — só olha para o
código de saída e depois **imprime** a contagem. Nunca exige que ela seja maior que zero.

Encontrei-o por acidente, e o acidente é a parte útil: corri a prova com o Node desta
shell, que é **23.11.0**, e o repositório fixa **22.23.2**. Em Node 23 o relatório do
corredor de testes é `spec`, não TAP, por isso não há linhas `^ok ` nem `# pass N`. Saída:

```
1. Com as políticas LIGADAS — os quatro casos têm de passar
  ok    0 grupos verdes,  asserções          ← VERDE, com zero medido
```

E o passo 2 fica pior: os discriminadores procuram marcadores TAP que também não existem,
e concluem *"caso 2 continuou verde sem política — não estava a medir o RLS"*. A prova
acusa o produto de um defeito que não tem.

Isto é exactamente a família que o próprio E03 defende noutro sítio. O JR escreveu, e bem,
*"sem política e sem contexto, o runtime vê 2 marcas — a base está viva e cheia"*: uma
guarda contra medir uma base vazia. **Faltou a mesma guarda contra a prova não ter
corrido.** O instrumento protegeu-se da população zero e não se protegeu de si próprio.

Numa máquina onde a versão do Node não seja a fixada — a minha shell, um portátil novo, um
runner diferente — a prova mais importante do produto pode dizer verde sem medir uma linha.

## Para fechar o E03

1. O passo 1 falha se os grupos ou as asserções forem zero, e diz porquê.
2. O formato deixa de ser adivinhado: `--test-reporter=tap` explícito, ou a versão do Node
   verificada à cabeça e recusada se não for a do `.nvmrc`.
3. **Controlo negativo do próprio controlo negativo**: correr a prova com um Node diferente
   (ou com o relatório trocado) e exigir que ela **falhe alto**, em vez de passar a zero.
4. Voltar a declarar. Revejo outra vez.
